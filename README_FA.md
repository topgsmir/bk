# bk — هسته و پکیج‌های مستقل

نگهدارنده: **topgsmir**

> Based on BackPack by Amin Mohammadi (AminMGMT)
> https://github.com/AminMGMT/BackPack

دستور `bk` یک منوی مشترک باز می‌کند، اما بک‌پک و پکیج‌های ۲ و ۳ دو برنامهٔ
مستقل هستند. کد، وابستگی‌ها و تست‌های آن‌ها از هم جدا شده‌اند.

| بخش | محل کد |
| --- | --- |
| نسخهٔ اصلی و دست‌نخوردهٔ BackPack | `upstream/BackPack` |
| اصلاحات اختصاصی هسته، نام و کلید انتشار bk | `integration` |
| پکیج‌های ۲ و ۳ و ابزارهایشان | `addons` |
| منوی مشترک | `main.go` |

برای استفاده: `bk`، `bk core`، `bk package2` یا `bk package3`.
مدیریت پکیج‌های ۲ و ۳ با `bk manage-addons` هم باز می‌شود. پنل وب متعلق به
هستهٔ بک‌پک است. تنظیمات در مسیرهای قبلی می‌مانند و دستور سرویس‌های موجود
نیازی به بازنویسی ندارد.

برای ساخت، Go 1.26.9 یا جدیدتر، Git و Make لازم است:

```sh
make build
make check
./bk components
```

خروجی همچنان یک فایل `bk` است تا نصب امضاشده، آپدیت و بازگشت به نسخهٔ قبلی
با قالب موجود کار کنند. این فایل دو برنامهٔ مستقل را داخل خودش نگه می‌دارد و
هرکدام را جدا اجرا می‌کند.

برای آپدیت بعدی، ابتدا commit نسخهٔ اصلی را بررسی کن و SHA کاملش را بده:

```sh
python3 scripts/sync-upstream.py --commit REVIEWED_40_CHARACTER_SHA --check-only
python3 scripts/sync-upstream.py --commit REVIEWED_40_CHARACTER_SHA
make check
```

این دستور فقط بخش upstream را به‌روز می‌کند. کد داخل `addons` تغییر نمی‌کند.
اگر اصلاحات اختصاصی هسته با نسخهٔ جدید تداخل داشته باشند، عملیات متوقف می‌شود
و نسخهٔ فعلی حفظ می‌شود تا همان تداخل مشخص بررسی شود. جداسازی، تداخل پکیج‌ها
با کد اصلی را حذف می‌کند؛ سازگاری پروتکل‌های جدید همچنان باید بررسی شود.

کد تولیدشده در `.build/core` قابل‌ویرایش دائمی نیست؛ اصلاحات هسته باید در
`integration` ثبت شوند. جزئیات در [معماری](docs/architecture.md) و
[راهنمای انتشار](docs/publishing.md) آمده است.
